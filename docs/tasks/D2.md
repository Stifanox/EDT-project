# D2 – Repozytorium SQLite + przechowywanie plików

**Właściciel:** O1 · **Zależności:** !P0 · **Status:** patrz [`PROGRESS.md`](../../PROGRESS.md)

## Cel
Trwałe przechowywanie dokumentów i metadanych między uruchomieniami aplikacji.

## Zakres
- `SqliteDocumentRepository` implementujący `DocumentRepository`.
- Tabela `documents` (id, name, text, source_type, language, added_at ISO, size_bytes, num_pages,
  content_hash UNIQUE, metadata JSON).
- Zapis oryginału pliku w `data/files/<id><ext>` (do pobrania w widoku dokumentu) i usuwanie go razem z dokumentem.
- Podmiana w fabryce `_make_repository()`.

## Pliki (własność)
- `edt/storage/sqlite_repo.py` – nowy
- `edt/storage/files.py` – nowy (zapis/odczyt/usuwanie oryginałów)
- `edt/services.py` → tylko `_make_repository()`
- `tests/contracts/test_repository_contract.py` → dopisanie fabryki do `REPO_FACTORIES`
- `tests/test_storage.py` – nowy

## Kontrakt / API
`DocumentRepository` z `edt/interfaces.py`. Dodatkowo (poza protokołem) np.
`original_path(doc_id) -> Path | None` dla widoku D5.

## Kryteria akceptacji
- [x] `SqliteDocumentRepository` przechodzi `test_repository_contract.py` (także z `:memory:`)
- [x] Dane przetrwają restart aplikacji (test: zapis → nowe połączenie → odczyt)
- [x] `content_hash` unikalny, a duplikat nie jest dodawany drugi raz
- [x] Oryginał pliku zapisany w `data/files/` i usuwany razem z dokumentem
- [x] `_make_repository()` zwraca repozytorium SQLite (`config.DB_PATH`)
- [x] Usunięcie dokumentu nie zostawia osieroconych danych w tabelach O1

## Wskazówki
- `edt.db.connect()` ustawia `check_same_thread=False` i WAL. Streamlit działa wielowątkowo, więc zapisy rób w `with conn:`.
- Tabelę `entities` tworzy O3 (N2). Nie dodawaj do niej kluczy obcych. O3 sam reaguje na `remove_document`.

## Notatki z realizacji
_2026-11-04, O1_

**Co powstało**
- `edt/storage/sqlite_repo.py`: `SqliteDocumentRepository(conn)` z tabelą `documents`
  (unikalny częściowy indeks na `content_hash`, indeks na `added_at`) i blokadą `RLock`,
  bo Streamlit odpytuje bazę z wielu wątków.
- `edt/storage/files.py`: `FileStore` (`data/files/<doc_id><ext>`) z zapisem atomowym,
  `path/read/delete/prune` i ochroną przed path traversal w `doc_id`.
- `edt/storage/errors.py`: `DuplicateDocumentError`.
- `edt/services.py`: `_make_repository()` zwraca SQLite (`config.DB_PATH`). Nowa fabryka
  `_make_file_store()`, pole `AppServices.files`, metoda `AppServices.original_path(doc_id)`.
  `ingest_file` zapisuje oryginał, `delete_document` go usuwa, a `build_services` przy starcie
  usuwa pliki osierocone.
- Testy: kontrakt repozytorium (memory + sqlite, 3 nowe przypadki) i `tests/test_storage.py` (15 testów).

**Decyzje**
- Oryginały plików są poza repozytorium, w `FileStore` w `AppServices`. Protokół
  `DocumentRepository` się nie zmienił, a repozytorium nie musi znać bajtów pliku.
- `add()`: ten sam `id` nadpisuje rekord (jak w wersji in-memory), a ta sama treść pod innym `id`
  rzuca `DuplicateDocumentError`. Obie implementacje zachowują się identycznie, co sprawdza test kontraktowy.
- `added_at` zapisywane jako ISO 8601 ze strefą, `metadata` jako JSON (`ensure_ascii=False`,
  nieznane typy przez `str`). Kolejność `list()`: `added_at`, potem kolejność wstawienia.
- Fabryki czytają `config.DB_PATH` / `config.FILES_DIR` w chwili wywołania. Fixture
  `isolated_data_dir` (autouse, `tests/conftest.py`) daje każdemu testowi własny katalog tymczasowy.

**Dla D5:** pobranie oryginału przez `services.original_path(doc.id)`, które zwraca `Path | None`.

**Znane ograniczenia**
- Brak migracji schematu. Przy zmianie tabeli `documents` w przyszłości trzeba dodać prostą
  wersję schematu, np. `PRAGMA user_version` albo tabelę wersji per moduł.
